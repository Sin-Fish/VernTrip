# VernFlow 知识图谱与文件关联图施工子文档

## 1. 文档定位

本文档是 VernFlow 主施工文档在“知识图谱 / 文件关联 / 图增强 RAG / 前端图谱展示”方向上的子施工文档，用于指导后续一段时间的：

- 后端文件关系层建设
- 资料库关联视图建设
- 图增强 RAG 接入
- 知识图谱后续演进路线

本文档默认继承以下上位文档目标：

- `docs/V0文档/文脉VernFlow_项目施工文档_v2.0_细化版.docx`
- `docs/V0文档/文脉VernFlow_比赛作品报告.docx`
- `docs/RAG可插拔重构施工子文档.md`
- `docs/RAG可插拔调研报告.md`

## 2. 总目标与边界

### 2.1 总目标

把当前系统中已经具备的：

- 文档解析
- chunk 索引
- embedding 检索
- graph strategy 接口
- random walk 重排能力

进一步组织成一套：

1. **后端真能用的图增强 RAG**
2. **前端真能展示的文件关联图**
3. **后续可平滑演进到知识图谱 / GraphRAG**

的中长期方案。

### 2.2 当前阶段的核心目标

当前阶段不追求一步到位做“完整知识图谱系统”，而是先完成：

1. 后端“文件关系层”
2. 资料库“关联视图”
3. 文件关系对 RAG 的轻量增强接入

### 2.3 当前阶段不做的事

1. 不先做完整实体级知识图谱
2. 不先做通用本体设计
3. 不先做图数据库迁移
4. 不先做复杂的全局力导向大图
5. 不先把 chunk / 概念 / 文件 / 任务全部暴露给前端

## 3. 当前现状

### 3.1 已有基础

项目当前已经具备以下图谱前置基础：

1. **文档解析与 chunk 索引**
   - 工作区文件可解析、切块、持久化
   - 后端已有 document / chunk index

2. **向量检索**
   - 已有 dense / hybrid 检索链
   - 已有 embedding 模型接入

3. **RAG 分层结构**
   - retriever
   - selector
   - graph strategy
   - generator

4. **图策略接口**
   - 后端与 AI 端已经有 graph strategy 概念
   - 随机游走重排已经落地

5. **前端图形展示基础**
   - 工作台已有图形画布、节点布局、缩放拖拽能力
   - 可复用为资料库关联图的实现基础

### 3.2 当前缺口

当前还缺以下关键能力：

1. 文件与文件之间的关系存储层
2. 关系构建服务
3. 资料库中的关系图视图
4. 关系解释层
5. 图增强 RAG 与关系图之间的统一数据流

## 4. 设计原则

### 4.1 先做文件关联图，不一步上完整知识图谱

第一阶段只做：

- 节点：文件
- 边：文件与文件的关系

而不直接做：

- 实体节点
- 关系抽取
- 实体归一化
- 图数据库

原因：

1. 更符合当前项目成熟度
2. 更容易和资料库页面结合
3. 更容易让用户理解
4. 后端更容易真实用起来

### 4.2 图必须先服务后端，再服务前端

知识图谱不能先做成“好看但没用的图”。

它必须先能：

1. 增强检索召回
2. 解释证据关系
3. 支持关系扩展与重排

然后前端才展示这张图。

### 4.3 资料库是第一落点

第一版前端图谱不放：

- 文档助手主视图
- 工作台主视图
- 独立一级菜单

而是放在**资料库**里，作为：

- `列表视图`
- `关联视图`

的切换模式。

原因：

1. 用户此时的关注对象就是“文件”
2. 文件关系图和资料库语义天然一致
3. 不会和工作台执行图产生竞争
4. 不会让文档助手主交互变重

### 4.4 第一版只做聚焦图，不做全库大图

默认交互应为：

1. 选中文件
2. 展示该文件的一跳关系
3. 最多展开前 `5~10` 个最相关文件

而不是一上来把整个库画成一张全局星空图。

## 5. 第一阶段目标架构

### 5.1 数据模型

第一阶段新增“文件关系层”，建议新增以下核心结构：

#### A. 文件关系表

`rag_file_relation`

字段建议：

- `id`
- `workspace_id`
- `source_file_path`
- `target_file_path`
- `relation_type`
- `score`
- `shared_terms_json`
- `cohit_count`
- `updated_at`

#### B. 关系证据表

`rag_file_relation_evidence`

字段建议：

- `id`
- `relation_id`
- `evidence_type`
- `source_chunk_id`
- `target_chunk_id`
- `summary`
- `score`

### 5.2 节点与边

#### 节点

第一阶段只支持：

- `file`

#### 边

第一阶段建议先支持三类：

1. `semantic_similar`
   - 文件语义相近
   - 来源：chunk embedding 聚合相似度

2. `shared_concepts`
   - 文件共享关键词/概念
   - 来源：chunk 内高频术语或 selector concept features

3. `co_hit`
   - 文件在问答/任务中经常一起命中
   - 来源：assistant / workbench 运行日志统计

## 6. 关系构建策略

### 6.1 语义相近关系

输入：

- 某文件下所有 chunk 向量

做法：

1. 按文件聚合 chunk embedding
2. 计算文件间相似度
3. 取高于阈值的文件对

输出：

- `semantic_similar`

### 6.2 共享概念关系

输入：

- 文件的 chunk 文本

做法：

1. 抽取高频术语 / 关键短语
2. 计算两文件共享概念交集
3. 交集达到阈值则建边

输出：

- `shared_concepts`

### 6.3 共同命中关系

输入：

- assistant 会话记录
- workbench 运行记录

做法：

1. 统计哪些文件经常共同出现在同一次问答或任务中
2. 形成共现计数
3. 达阈值后生成 `co_hit`

输出：

- `co_hit`

## 7. 图增强 RAG 接入方案

### 7.1 第一阶段接法

先不改主检索器结构，只做轻量增强：

1. 先按原 RAG 主链召回 top chunks
2. 根据 top chunks 映射到所属文件
3. 用文件关系图做一跳扩展
4. 把扩展后的文件下相关 chunk 补回候选池
5. 再交给 selector / graph strategy / generator

### 7.2 图的角色

图在后端 RAG 中的角色是：

1. **候选扩展器**
2. **关系重排器**
3. **证据解释层**

而不是直接替代 retriever。

### 7.3 与现有 graph strategy 的关系

当前已有：

- `random_walk_rerank`

第一阶段不替换它，而是：

1. 先新增文件关系层
2. 先做文件图扩展
3. 后续再考虑让 `random_walk` 从 chunk 临时图升级为文件关系图或概念关系图上的游走

## 8. 资料库关联视图方案

### 8.1 MVP 交互

进入资料库后：

1. 默认显示列表视图
2. 切换到“关联视图”
3. 选中文件后显示该文件的关系子图

### 8.2 中间画布展示

默认展示：

- 当前文件节点
- 它最相关的前 `5~10` 个文件
- 文件之间的关系边

### 8.3 右侧说明面板

点节点或边时显示：

- 文件名
- 所属目录
- 关系类型
- 关系分数
- 共享关键词
- 共同命中的任务/问答
- 关系证据摘要

### 8.4 第一版不做的交互

1. 不做全库一次性铺开
2. 不做概念节点混排
3. 不做复杂筛选器
4. 不做编辑关系

## 10. 风险与注意事项

### 10.1 图不要先做得太大

第一版如果直接全库铺开，最容易出现：

1. 看不懂
2. 卡顿
3. 无法解释

### 10.2 关系必须能解释

每条边都必须有：

- 类型
- 分数
- 证据
- 共享术语或共同命中原因

否则图会退化成装饰性组件。

### 10.3 不要与工作台执行图混用

工作台当前图是“执行流程图”，不是知识图谱。  
第一阶段不要把两张图混在一张画布里。

### 10.4 图谱构建应支持增量更新

文件关系层不能每次都全量重建。  
需要支持：

1. 单文件更新
2. 局部关系重算
3. 后续后台索引任务接入

## 11. 验收标准

第一阶段完成后，至少应满足：

1. 后端可计算并存储文件间关系
2. 资料库中可切换到“关联视图”
3. 选中文件后能看到其关联文件
4. 每条关系边都有解释
5. 关系数据不是 mock，而是由真实文件内容计算

第二阶段完成后，至少应满足：

1. assistant 可在内部使用文件关系扩展候选
2. workbench 可在内部使用文件关系增强整理/检索
3. 图谱与 RAG 主链有真实耦合，而非纯展示

---

## 12. 当前推荐落地顺序

建议按以下顺序推进：

1. 建立文件关系表与构建服务
2. 做资料库关联视图
3. 做关系解释侧栏
4. 接入 assistant / workbench 的图增强召回
5. 再评估是否进入概念级知识图谱

## 14. 一句话路线结论

当前最稳、效果最好、也最符合项目现状的路线是：

**先做资料库里的“文件关联视图”，并让后端先以文件关系层增强 RAG；再从文件关系图平滑演进到概念级知识图谱。**
