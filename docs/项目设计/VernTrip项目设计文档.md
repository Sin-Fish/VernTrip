## 1. 文档信息

| 项目 | 内容 |
| --- | --- |

| 文档性质 | 项目总体设计说明 |
| 当前版本 | V1.0 |
| 适用阶段 | 需求分析、原型设计、系统开发、竞赛演示 |

## 2. 编制目的

本文档用于明确 VernTrip 的建设目标、用户范围、功能边界、核心业务流程和阶段性实施内容，作为产品设计、技术设计、任务拆分和项目验收的依据。

本文档重点说明以下事项：

1. 游客端与商家管理端的职责划分。
2. 文旅资源、游客需求、旅游产品和营销内容之间的业务关系。
3. 个性化旅行方案抽选功能的业务规则。
4. OpenClaw 在系统中的运行方式、权限范围和审计要求。
5. 竞赛版本的开发范围和验收标准。

## 3. 项目概述

### 3.1 建设背景

景区、酒店和餐饮等文旅业态普遍存在服务内容相似、游客需求识别不足、营销成本较高、产品更新周期较长等问题。商家掌握的资源资料通常分散在文档、表格和业务系统中，缺少统一的知识管理和智能辅助能力；游客则需要在多个平台之间查询信息并自行组合路线。

VernTrip 以文旅资源和游客需求为基础，为游客提供咨询、行程规划和个性化方案抽选服务，为商家提供资源管理、需求分析、产品设计、营销内容生成和运行审计功能。

### 3.2 项目定位

VernTrip 采用游客端与商家管理端相结合的产品结构。游客端承担需求采集和服务展示职能，商家管理端承担资源维护、产品设计和运营分析职能。

系统建设以商家管理端为重点，游客端应具备完整但适度的使用流程。建议开发投入按以下比例安排：

- 商家管理端及平台能力：约 65%。
- 游客端：约 35%。

### 3.3 建设目标

1. 建立统一的景区、住宿、餐饮、活动和文化资源库。
2. 将游客的日期、预算、兴趣和同行人群转换为结构化需求。
3. 生成满足约束条件的旅游路线和文旅产品推荐。
4. 根据聚合需求辅助商家设计和调整文旅产品。
5. 辅助生成面向不同平台和客群的营销内容。
6. 通过 OpenClaw Skills 和工具完成资料读取、方案生成、检查和审计。
7. 保证模型调用过程具备权限控制、来源引用和人工确认机制。

### 3.4 建设边界

竞赛版本不以在线交易为主要目标，暂不建设完整的库存、支付、退款、结算和票务系统。产品采用、收藏和转化可使用业务状态进行模拟。

下列内容不纳入第一阶段：

- 实时房态、票务和餐位库存对接。
- 完整订单和财务结算流程。
- 自动修改正式价格。
- 未经审核的自动发布和批量营销触达。
- 数字人直播及复杂社交社区。

## 4. 用户与权限

### 4.1 游客

游客可以维护个人偏好、提交单次出行需求、生成或抽选旅行方案、收藏行程并提交反馈。游客只能查看已发布且处于有效期内的文旅资源和产品。

### 4.2 商家用户

商家用户包括景区、酒店、民宿、餐饮、旅行社、研学机构和文旅内容运营人员。商家只能管理所属租户的资源、产品和营销内容，并查看经过匿名化和聚合处理的游客需求数据。

### 4.3 平台运营人员

平台运营人员负责商家审核、公共资源管理、内容合规检查、信息时效管理和系统运行监督。竞赛版本可将平台运营能力作为商家管理端中的高级权限，不单独建设第三套前端。

### 4.4 管理端角色

| 角色 | 主要权限 |
| --- | --- |
| 商家管理员 | 成员管理、资源管理、产品审核、发布和数据查看 |
| 产品运营 | 需求分析、产品设计、产品编辑和效果查看 |
| 内容运营 | 营销内容生成、编辑、提交审核和归档 |
| 数据查看员 | 查看运营指标和聚合需求，不具备修改权限 |
| 平台运营员 | 商家审核、公共资源管理、违规处理和系统审计 |

## 5. 总体业务设计

### 5.1 双端关系

游客端与商家管理端共用文旅资源、旅游产品、需求标签和 OpenClaw 能力，但使用不同的界面和权限策略。

```text
商家录入并审核文旅资源
          ↓
资源和产品发布至游客端
          ↓
游客提交需求并获得方案
          ↓
收藏、采用、替换和反馈形成匿名化数据
          ↓
管理端生成需求分析和产品改进建议
          ↓
商家创建或调整产品并重新发布
```

### 5.2 主要业务对象

| 对象 | 说明 |
| --- | --- |
| 游客画像 | 游客的长期偏好、排除项和隐私设置 |
| 出行需求 | 某次出行的日期、预算、目的地、同行人群和约束 |
| 文旅资源 | 景区、住宿、餐饮、活动、文化内容和公共服务信息 |
| 旅游产品 | 商家组合形成的线路、套餐或主题体验产品 |
| 旅行方案 | 针对一次游客需求生成的具体行程 |
| 抽选签池 | 可参与个性化方案抽选的候选产品和规则集合 |
| 抽选记录 | 候选范围、抽选结果、解释和用户反馈 |
| 营销内容 | 围绕产品生成的文案、脚本和宣传资料草稿 |
| 需求洞察 | 对匿名化游客需求和行为进行汇总后的分析结果 |
| Agent 运行记录 | OpenClaw 的执行状态、工具、耗时、Token 和错误信息 |

## 6. 游客端功能设计

游客端采用移动端优先的设计方式，主要使用表单、卡片、时间轴和地图展示信息。

### 6.1 游客画像

游客画像包含以下信息：

- 常用出发地和可接受出行距离。
- 自然、人文、非遗、美食、亲子、摄影、夜游等兴趣标签。
- 常用预算区间。
- 住宿、餐饮和交通偏好。
- 行程节奏偏好。
- 饮食禁忌、健康情况和无障碍要求。
- 明确不接受的活动或场所类型。

游客应能够查看、修改、暂停使用或清除画像信息。系统不得因一次点击长期改变用户画像。

### 6.2 出行需求采集

每次生成方案前，系统至少采集以下条件：

- 出行日期和天数。
- 出发地和目的地范围。
- 人数及同行关系。
- 总预算或人均预算。
- 交通方式。
- 本次兴趣和排除项。
- 行程节奏。

长期画像可作为默认值，但单次出行需求应具有更高优先级。

### 6.3 智能咨询

智能咨询用于回答景区、住宿、餐饮、交通和文化内容相关问题，具体要求如下：

1. 优先使用已审核的资源和知识库内容。
2. 对价格、开放时间等时效性信息标明来源和核验时间。
3. 无法确认的信息不得作为确定事实输出。
4. 支持围绕当前出行需求和已生成方案继续提问。

### 6.4 个性化旅行方案

系统根据游客需求生成一日或多日旅行方案。方案应包括：

- 分日、分时段的行程安排。
- 景区、住宿、餐饮和体验活动。
- 地点顺序和交通建议。
- 预算估算及主要费用构成。
- 推荐理由和适配条件。
- 闭馆、天气、拥堵等风险提示。
- 可替换项目和备选方案。

用户可以对局部内容进行调整，包括降低预算、放慢节奏、替换景点、增加餐饮或调整住宿。局部调整不应强制重新生成全部行程。

### 6.5 收藏、分享与反馈

- 收藏旅行方案和抽选结果。
- 生成适合移动端查看的分享页面。
- 导出简要行程单。
- 对整体方案和单项资源进行评价。
- 标记方案是否实际采用。

系统应区分浏览、收藏和实际采用，避免将弱行为直接视为明确偏好。

## 7. 个性化旅行方案抽选模块

### 7.1 功能定义

游客端设置“旅行抽签”入口。该功能根据游客画像、单次出行条件、历史反馈和平台产品库，从满足条件的候选方案中抽选一份旅行计划。

该功能的正式名称为“个性化旅行方案抽选”，游客端可使用“旅行抽签”“周末去哪签”等名称展示。

抽选过程属于受约束推荐，不采用无条件随机方式。

### 7.2 使用场景

- 游客尚未确定目的地，需要获得出行建议。
- 游客已确定日期和预算，但没有明确主题。
- 游客希望在原有偏好之外尝试新内容。
- 游客需要替换现有行程中的半天或一天安排。
- 平台开展节庆、非遗、亲子等专题活动。

### 7.3 抽选条件

抽选前必须确认以下硬约束：

- 可用日期或时长。
- 预算上限。
- 出发地、目的地范围或可接受距离。
- 同行人群。
- 健康、饮食和无障碍要求。
- 明确排除项。

硬约束不参与随机调整。候选方案违反任一硬约束时，不得进入签池。

### 7.4 抽选模式

| 模式 | 适用情况 | 规则说明 |
| --- | --- | --- |
| 稳妥模式 | 用户希望降低决策风险 | 以历史偏好和高匹配资源为主，保留少量新内容 |
| 探索模式 | 用户愿意尝试不同主题 | 在满足主要偏好的基础上提高新颖性权重 |
| 随机模式 | 用户希望获得较强的意外性 | 提高未体验内容的权重，但仍执行全部硬约束和质量检查 |

模式只影响候选排序和抽选权重，不改变预算、安全和适用人群等限制。

### 7.5 候选方案生成

候选方案按照以下流程生成：

1. 读取游客画像和本次出行需求。
2. 排除预算、日期、距离和人群条件不符的资源。
3. 读取已发布旅游产品和专题签池。
4. 计算偏好匹配、路线可行性、资源质量和信息完整度。
5. 根据抽选模式调整新颖性和重复体验权重。
6. 生成若干完整候选方案。
7. 检查路线、预算、营业状态、适用人群和资料有效期。
8. 从合格候选方案中进行加权抽选。

### 7.6 评分原则

候选方案可采用规则评分与加权抽选相结合的方式。第一阶段不要求训练复杂推荐模型。

```text
候选得分 =
偏好匹配度
+ 时间与距离适配度
+ 预算适配度
+ 同行人群适配度
+ 季节适配度
+ 资源质量
+ 新颖性权重
- 重复体验惩罚
- 负反馈惩罚
- 信息缺失和时效风险惩罚
```

具体权重由抽选模式、用户反馈和运营配置共同决定。

### 7.7 抽选结果

抽选结果应包括：

- 方案主题和简短签文。
- 一日或多日时间安排。
- 景区、住宿、餐饮和活动建议。
- 预算区间和交通说明。
- 抽选依据，包括主要偏好和新增体验。
- 资料来源和待确认事项。
- 接受、重新抽选、局部调整、收藏和分享操作。

签文用于改善展示效果，不得替代具体行程和事实信息。

### 7.8 重新抽选规则

重新抽选应优先收集原因，例如预算过高、路线过远、活动不感兴趣或节奏不合适。系统根据原因调整候选范围，避免在相同条件下重复生成近似方案。

为控制模型调用成本，可在首次请求时生成多份候选方案，后续抽选优先从候选集合中切换。局部不满意时应优先使用局部替换，而不是重新生成全部行程。

### 7.9 偏好更新

| 用户行为 | 建议处理方式 |
| --- | --- |
| 收藏、接受、实际采用 | 作为正向信号，实际采用权重最高 |
| 主动替换或明确不喜欢 | 作为负向信号 |
| 浏览或多次咨询 | 作为弱信号，不直接形成长期偏好 |
| 清除历史或关闭个性化 | 停止使用相关历史数据 |

行为权重应随时间衰减。用户可以查看主要偏好标签并进行修正。

### 7.10 商家侧管理

商家可以将已审核产品申请加入专题签池，并查看以下聚合指标：

- 入池次数。
- 抽中次数。
- 接受、收藏和采用次数。
- 重新抽选次数及主要原因。
- 不同抽选模式下的表现。

商家不得查看与经营分析无关的游客个人信息。推广产品进入签池时应明确标识，不得将推广权重作为用户偏好进行解释。

## 8. 商家管理端功能设计

管理端采用桌面端优先的设计方式，强调信息完整、操作可追溯和任务处理效率。

### 8.1 运营总览

运营总览用于集中展示：

- 游客需求数量及变化趋势。
- 热门目的地、主题、预算和同行人群。
- 产品曝光、匹配、收藏和采用情况。
- 旅行抽选的入池、抽中、接受和重新抽选情况。
- 咨询热点和未解决问题。
- 资源过期、资料冲突和待审核事项。
- OpenClaw 运行成功率、延迟、Token 和异常数量。

总览页面应同时提供待处理事项入口，避免仅展示统计图表。

### 8.2 文旅资源与知识库

资源范围包括：

- 景区、博物馆和文化场馆。
- 酒店、民宿、营地和房型。
- 餐厅、地方美食和餐饮套餐。
- 非遗、研学、演出、夜游和节庆活动。
- 交通、公共服务、安全和政策信息。

资源主要字段包括名称、类型、地址、位置、标签、适用人群、开放时间、价格、服务能力、图片、资料来源、核验时间、有效期和所属商家。

资源状态包括草稿、待审核、已发布、已过期和已停用。游客端只使用已发布且有效的资源。

知识库应支持资料上传、文本抽取、引用预览、重复识别、冲突提示和过期提醒。

### 8.3 游客需求分析

需求分析基于匿名化和聚合数据，主要包括：

- 客群、预算、偏好和出行时间分布。
- 热门咨询和路线主题。
- 缺少可匹配产品的需求。
- 经常被替换或拒绝的资源。
- 产品匹配和采用情况。
- 旅行抽选的模式分布和重新抽选原因。

分析结果应标明统计时间和样本量。数据量不足时不得给出确定性结论。

### 8.4 AI 文旅产品设计

商家根据需求分析和现有资源创建旅游产品。输入信息包括目标客群、季节、预算、可用资源、服务范围、必要项目和排除项。

系统生成的产品草稿应包括：

- 产品名称和主题。
- 目标客群和适用场景。
- 行程和资源组合。
- 成本估算和建议价格区间。
- 服务标准和风险事项。
- 闭馆、满房和天气异常时的替代方案。
- 与现有产品的差异。
- 适合加入的专题签池。

产品生成后进入草稿状态，经人工编辑、检查和审核后发布。

### 8.5 AI 营销内容管理

营销内容以已确认的文旅产品为依据，可生成：

- 小红书文案。
- 公众号文章。
- 短视频脚本和分镜说明。
- 海报标题和活动口号。
- 产品详情页内容。
- 客服推荐话术。

生成时应指定发布平台、目标客群、表达风格和篇幅。系统应检查价格、开放时间、服务承诺和夸大宣传。所有内容默认保存为草稿，审核后方可发布或导出。

竞赛版本不要求直接接入全部内容平台。

### 8.6 客源匹配

客源匹配用于计算游客需求与旅游产品之间的适配程度。结果应包括匹配分数、匹配理由和不匹配原因。

主要功能包括：

- 为游客端推荐合适产品。
- 为旅行抽选建立候选范围。
- 查看产品曝光、收藏、采用和反馈。
- 识别未被现有产品覆盖的需求。
- 将未满足需求提交至产品设计模块。

竞赛版本可使用“采用”状态模拟转化，不建设真实交易流程。

### 8.7 OpenClaw 运行管理

运行管理页面用于查看：

- Agent Run 状态和时间。
- 使用的 Skill 和工具。
- 使用的资料范围和引用来源。
- 执行步骤、耗时和 Token。
- 固定错误码和降级结果。
- Shadow 模式下新旧助手结果对比。
- 涉及写入、审核和发布的人工确认记录。

页面不得展示 Gateway Token、服务 Token、用户隐私、服务器绝对路径或完整内部提示内容。

### 8.8 商家和成员管理

- 商家基本资料和状态管理。
- 门店和资源归属管理。
- 成员邀请、停用和角色分配。
- 发布、删除和批量操作权限。
- 操作审计和异常提示。

第一阶段可以按单商家场景实现，但数据库和服务接口应保留租户字段。

## 9. OpenClaw 设计

### 9.1 系统职责

OpenClaw 作为系统内部的智能执行引擎，负责识别任务、选择 Skill、调用受控工具和生成结果。用户身份、商家身份、工作区范围和权限由 VernTrip 后端维护，不作为模型自由填写的参数。

### 9.2 Skills 规划

| Skill | 职责 | 优先级 |
| --- | --- | --- |
| `tourism-consult` | 文旅咨询和来源引用 | P0 |
| `traveler-profile` | 提取和更新出行需求 | P0 |
| `itinerary-plan` | 生成和调整旅行方案 | P0 |
| `travel-lottery` | 生成候选签池并执行方案抽选 | P0 |
| `tourism-product-design` | 生成文旅产品草稿 | P0 |
| `tourism-marketing` | 生成营销内容草稿 | P0 |
| `customer-demand-match` | 需求与产品匹配 | P1 |
| `tourism-fact-check` | 检查时效信息和宣传表述 | P1 |
| `tourism-insight` | 生成经营分析摘要 | P1 |

### 9.3 工具分类

| 风险等级 | 工具类型 | 执行策略 |
| --- | --- | --- |
| 低 | 资料读取、资源查询、聚合查询、事实检查 | 可自动执行并记录 |
| 中 | 创建产品草稿、营销草稿、候选方案 | 可自动执行，保留审计记录 |
| 高 | 修改正式价格、发布产品、批量触达 | 必须人工确认 |
| 禁止 | 越租户访问、读取密钥、任意系统命令 | 不向模型提供 |

### 9.4 引擎切换

OpenClaw 接入采用以下阶段：

1. `legacy`：仅使用原有助手。
2. `shadow`：原助手正常返回，OpenClaw 在后台执行并记录结果。
3. `canary`：少量请求由 OpenClaw 正式处理。
4. `openclaw`：OpenClaw 作为主引擎，原助手作为故障回退。

当前项目已完成 Shadow 基础链路，后续应先建设对比和评测能力，再进入 Canary 阶段。

## 10. 数据与安全要求

### 10.1 数据要求

- 游客长期画像与单次出行需求分开存储。
- 游客行为数据区分浏览、收藏、采用和明确反馈。
- 商家数据包含租户标识和资源归属。
- AI 生成结果保存来源、版本和审核状态。
- 时效信息保存来源、核验时间和有效期。
- Agent 运行记录保存状态、耗时、Token 和固定错误码。

### 10.2 安全要求

- 游客不能读取未发布资源和商家内部资料。
- 商家不能访问其他租户数据。
- 商家只能查看匿名化需求分析，不直接获取游客个人画像。
- 模型不能通过工具参数声明用户或商家身份。
- 密钥不得进入浏览器、前端构建产物和运行日志。
- 文件、网页和检索内容均按不可信输入处理。
- 发布、删除和正式数据修改必须记录操作人和时间。

### 10.3 推荐透明度

- 游客能够查看推荐和抽选的主要依据。
- 推广内容应明确标识。
- 商业推广权重不得表述为用户偏好。
- 用户可以关闭个性化并清除历史偏好。

## 12. 非功能要求

### 12.1 性能

- 普通查询接口应在 2 秒内返回。
- AI 请求应设置超时和取消机制。
- Shadow 请求不得延迟游客端主响应。
- 抽选模块应复用候选方案，减少重复模型调用。

### 12.2 可用性

- OpenClaw 不可用时保留原助手回退能力。
- AI 生成失败时不丢失用户已提交的需求。
- 资源信息不完整时明确提示，不生成确定性结论。
- 草稿、审核和发布状态必须可恢复。

### 12.3 可审计性

- 记录关键工具调用和结果状态。
- 记录产品和内容的创建、修改、审核和发布时间。
- 对失败原因使用固定错误码。
- 审计记录中不保存密钥和无必要的完整用户文本。

平台能力：

### 13.2 P1：业务闭环完善

## 14. 验收标准

### 14.1 游客端

1. 能够根据日期、预算、兴趣和同行人群生成完整方案。
2. 方案包含路线、费用、推荐理由、备选内容和来源。
3. 旅行抽签只从满足硬约束的候选方案中选择。
4. 用户能够对方案进行局部调整、收藏和反馈。

### 14.2 商家管理端

1. 能够录入并审核景区、住宿、餐饮和活动资源。
2. 能够查看匿名化需求趋势和未满足需求。
3. 能够基于现有资源生成产品草稿并完成审核发布。
4. 能够基于产品生成营销内容并执行事实检查。
5. 能够查看旅行抽选和产品匹配的聚合效果。

### 14.3 OpenClaw

1. 能够通过可信会话读取授权范围内的资料。
2. 工具参数不包含可由模型伪造的用户或商家身份。
3. 写入和发布操作执行人工确认。
4. 运行记录包含 Skill、工具、耗时、Token 和结果状态。
5. OpenClaw 失败不影响 Shadow 阶段的原助手响应。

## 15. 竞赛演示流程

演示采用“杭州亲子非遗两日游”场景：

1. 商家在管理端录入景区、酒店、餐饮和非遗体验资料并完成审核。
2. 游客提交周末两天、亲子出行、预算 3000 元、偏好非遗和美食的需求。
3. 系统生成包含预算、来源和备选方案的行程。
4. 游客使用探索模式进行旅行抽签，获得包含夜游和手作体验的候选方案。
5. 管理端显示匿名化需求及抽选反馈。
6. 商家根据需求创建亲子非遗产品草稿。
7. 系统生成对应的小红书文案和短视频脚本，并检查时效信息和宣传表述。
8. OpenClaw 运行页面展示相关 Skill、工具、引用、耗时和确认记录。

该流程覆盖智能咨询、个性化规划、景区服务、住宿、餐饮、营销、产品设计、客源匹配和 OpenClaw 运行规范。

## 16. 后续设计事项

进入详细设计前，需要进一步确认以下事项：

1. 游客端采用独立应用还是与现有前台共用路由和组件。
2. 商家端首批支持的商家类型和资源字段。
3. 行程地图使用的地图服务及调用限制。
4. 旅行抽签的候选数量、默认模式和权重配置方式。
5. 商家产品审核由商家管理员还是平台运营人员完成。
6. 竞赛演示数据的城市范围和资料来源。
7. Shadow 对比的评价指标和人工评分流程。
